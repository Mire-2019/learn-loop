# 往 B 站投稿（网页 cookie 通道）

读收藏夹/字幕之外，这个技能还管**投稿**。下面是这条通道的接口细节，**不要重新试错**。

## 验证状态（先说清楚哪些是跑通的、哪些还只是接口正确）

- **已实测跑通、并真的投出去了**：`nav` 验活；`preupload` → 整体 `PUT` 直传（`PUT_OK`）；封面（data URL 表单）；biliup **Python 包**的 `login_by_cookies` → `upload_file` → `cover_up` → `submit('web')` →
  **`{"code":0,"data":{"aid":117312686462006,"bvid":"BV1txhk65Eje"}}`**（分区 231，标题/封面/简介/标签全部落地）。
- **稿件状态怎么查**（投稿接口只回 aid/bvid，不给状态；公开接口在审核期回 `-404`，别据此以为失败）：
  `GET https://member.bilibili.com/x/web/archives?pn=1&ps=6` → `data.arc_audits[].Archive`
  **state：`-30` 审核中 / `0` 已通过（公开）**。
- **生产工具＝biliup 的 Python 包**（不是 Rust 命令行版）。

## 先验活：cookie 会失效，投稿任务的第一个动作是 `nav`

**2026-09-22 实测：手上三份 cookie 全失效**（`nav` 回 `-101 账号未登录`，连 `sid`/`buvid3` 都在但 SESSDATA 已死）。B 站**没有**设备码流程，只能扫码重新登录：
1. `GET https://passport.bilibili.com/x/passport-login/web/qrcode/generate` → `data.{url, qrcode_key}`
2. 把 `url` 画成二维码给用户扫（用 `qrcode` 库，560px 够扫）
3. 轮询 `GET /x/passport-login/web/qrcode/poll?qrcode_key=…`，**状态码在 `data.code` 里**（外层 `code` 只表示接口调用成功；这点搞错会立刻把"未扫码"当成"登录成功"，然后拿到一份空 cookie）：
   `86101` 未扫码 / `86090` 已扫码待确认 / `86038` 已过期 / `0` 成功
4. 成功后从响应头 `Set-Cookie` + `data.url` 的 query 里取 `SESSDATA / bili_jct / DedeUserID / DedeUserID__ckMd5`，写成 `cookie_info.cookies[]` 形状给 biliup，再 `nav` 复验一次才算数
5. 二维码 **170 秒**就过期 → 做成常驻进程自动换新码，别指望用户一次扫中


- 网页 cookie 不是永久的。实测某次开工时 `nav` 回 `-101 账号未登录`，而手上三份 cookie 文件（含 biliup 读的那份）其实是**同一份死 cookie**，换文件没有意义。
- 所以任何投稿任务的第一步永远是 `GET /x/web-interface/nav` 并**报出 `uname`/`mid`**。不要跳过这步直接开始渲染、合并、上传：等提交时才发现登录失效，前面所有准备都要重做，而 601 的频率限制让"重做"很贵。
- 失效后只能重新扫码（状态码在内层 `data.code`，坑见 SKILL.md §1）；新 jar 写入 `credentials/biliup-cookies.json`（600）之后**再用 `nav` 复验一次**才算真的拿到会话。
- 这一步适合做成常驻进程：一直持有活码、过期自动换、成功了立刻落盘。用户看到新码再扫即可，不需要有人守在旁边。

## 结论速查

| 环节 | 走法 | 实测结果 |
|---|---|---|
| 验活 | `GET api.bilibili.com/x/web-interface/nav` | `code=0 isLogin=True` |
| 视频 | `GET member.bilibili.com/preupload` → `PUT {endpoint}/{upos_uri}?{put_query}`（头 `X-Upos-Auth`） | 小文件 `200 PUT_OK` |
| 封面 | `POST member.bilibili.com/x/vu/web/cover/up`，**form 表单** `cover=data:image/jpeg;base64,…` + `csrf` | 返回图床 URL |
| 投稿 | `POST member.bilibili.com/x/vu/web/add?csrf=<bili_jct>`，JSON body | 网页端在用 |
| 生产工具 | biliup 的 **Python 包**：`BiliBili` + `Data` + `login_by_cookies` | 登录取数已验证；投稿那步见下方「验证状态」 |

## 别踩的坑

1. **`biliup` 命令行（Rust）在有网页 cookie 的机器上不可用**：任何子命令前都做一次凭证校验，走 App 侧接口要
   `token_info.access_token` → `credential validation failed with Bilibili code -400`。`--submit web` 也救不了。
   → 用 **biliup 的 Python 包**（只吃网页 cookie）。`login_by_cookies` 要传**解析后的 dict**，传字符串会
   `TypeError: string indices must be integers`。
2. **`add/v3` 是死路**：字段怎么拼都回 `21001 参数错误`。网页端真正调用的是 v2 端点 `/x/vu/web/add`，
   且提交前要先 `GET /x/geetest/pre/add`。`videos[].filename` 用**去掉扩展名**的 upos 文件名，**不带 `cid`**。
3. **upos 的 `POST …?uploads&output=json` 申请分片会 `400 InvalidArgument`**（带不带 cookie、换参数都试过）；
   但**整体 PUT 直传是通的**（`?{put_query}`，query 由 preupload 返回，形如 `os=upos&profile=ugcfx%2Fbup`）。
   注意：**只直传不合并登记，投稿会回 `21613 上传过程中出现系统异常，请重新上传～`** → 生产链路走 biliup 的
   `upload_file`（内部 `?uploads` → 分片 → 合并 `profile=ugcupos/bup`）。
4. **封面不是 multipart**：multipart（含 wbi、`t`/`csrf` 任意组合）一律 `-400 请求错误`；必须 data URL 表单。
   图要 **16:10**（biliup 会自己裁）；官方建议 ≥1146×717、≤5 MB、jpeg/png。
5. **投稿接口有频率限制**：短时间内多次 `preupload` → `406 {"code":601,"message":"您上传视频过快，请您稍作休息后再继续"}`。
   → **正式投稿必须一次成型**：成片、封面、简介、标签、分区全部定稿后再传，别拿正式号反复试。
6. **`cover_up` 返回的 URL 要去掉 `http:` 前缀**再放进投稿 payload（biliup 就是这么处理的）。
7. **创作中心稿件列表的 `stat` 全是 0，不能当数据用**：`member.bilibili.com/x/web/archives` 每条 `Archive.stat` 都回 `view:0/like:0`，按它排序得到一张全零的表。播放/点赞/收藏/评论一律取公开的 `GET api.bilibili.com/x/web-interface/view?bvid=…` 的 `data.stat`；创作中心那份只用来读 **标题 / 分区 / 时长 / `state`（`-30` 审核中 · `0` 已公开）**，以及确认稿件确实存在。
8. **提交后立刻用公开接口查会回 `-404 啥都木有`**——稿件还在审核队列里就是这样，不是投稿失败；成功以投稿接口回的 `aid/bvid` 为准，再回读创作中心看 `state` 转成 `0`。

## 成片技术参数（过平台再编码前自查）

- 1080p 纯静态画面用 `-crf 18` 只会压出 ~140 kbps，文字边角上平台二次转码会糊；
  改成 `-b:v 2500k -maxrate 4000k -bufsize 8000k`，并用 PSNR 与源图比对确认（实测 40.5 dB 属高保真）。
- 平台侧硬约束（官方规范）：≤4 GB、<5 h、推荐 mp4、≤60 Mbps、≤4096×4096、≤120 fps、
  关键帧间隔 ≥10 s、yuv420、音频 ≤320 Kbps/2 声道/48 kHz。
