# OV 模型轮换器：把「一次报错就永久判死」修掉（2026-09-22）

## 现场事实（都是实测读数）

- 上游聚合端点：`https://ws-8ipu42b1e3t5h3ow.cn-beijing.maas.aliyuncs.com/compatible-mode/v1`（阿里云百炼 MaaS，挂了多家：qwen 226、MiniMax 8、vanchin 8、ZHIPU 6、kimi 5、siliconflow 4、stepfun 2…）
- **模型总数 261**，轮换器按 EXCLUDE 过滤掉音频/图像/TTS 后剩 **163 个候选**
- 账本（`/home/ubuntu/rotator/ledger.json` → 容器内 `/data/ledger.json`）里只记了 **21 个模型**：11 capped、9 exhausted、1 active，累计 **14.1M token**
- 直连上游逐个试 100 个：**55 通 / 39 报「模型名无效或不支持」/ 5 个 403 / 1 个 429** → 外推 163 个候选里约 80–90 个真能用

## 真凶

`account()` 里用一条正则决定生死：

```python
if re.search(r"(quota|exhaust|insufficient|arrearage|limit|Forbidden|余额|额度)", err):
    e["status"] = "exhausted"      # ← 永久，没有回头路
```

两个问题叠加：

1. **一次失败就永久下架**：`exhausted` 之后再也不会被 `pick_and_reserve()` 选中。证据：9 个模型 `used = 0`（一次成功调用都没有）就被标成 `exhausted`。
2. **正则误伤**：`limit` 会命中 `rate limit`（429 限流）和 `max_tokens 超出区间` 这类**临时/参数**错误。于是一个刚上线的新模型，只因为一次限流就被永久下架 —— 等于把一份免费额度白扔。

后果：候选池看起来有 163 个，实际能用的被自己砍到 21 个；烧完就 `502 所有候选模型都用完了/都失败了`（OV 的技能上传因此 503）。

## 修法（改前已备份 `bailian_rotator.py.bak-<时间戳>`）

1. **判死 → 冷却**：`exhausted`/`cooldown` 都带 `retry_after`；**普通失败睡 3 小时**、明确欠费（`arrearage|insufficient|余额不足|free quota` 之类）**睡 24 小时**，到点自动放回 `active`。成功回来后立刻恢复。
2. **max_tokens 统一钳到 8192**；若上游回 `max_tokens 应在 [1,16384]` 这类 400，**按它给的区间改一次再打同一个模型**，不再把这个模型记成失败。
3. 由于免费额度本身会轮换/恢复，冷却机制顺带解决了「额度回来但模型还在黑名单里」的问题。

改完重启容器：`candidates=163 of 261`，连续 152 次请求 0 失败，OV 技能上传从 503 恢复成 **200**。

## 可复用的工具（都在 `/opt/data/ov-sync/`）

- `rotator_warm.py`（部署到 OV 机 `/tmp/`）：对候选池发极小请求，验证轮换器**连续可用性**
- `probe_upstream.py`：**绕过轮换器**直连上游逐个试模型 —— 因为轮换器忽略请求里的 `model` 字段（自己挑），经它探测永远只命中同一个模型，得不出"哪些候选真能用"的结论
- 读账本与候选数的正确姿势：`docker exec -i 模型轮换器 python3 - < probe.py`（容器里没有 wget，别指望 `wget`/`curl` 探 `轮换器网关`；轮换器绑的是 docker bridge 网关，不是 127.0.0.1）

## 教训

- **代理层的"失败"要分清临时/永久**：把「一次失败」等同于「永久不可用」，会让一个可轮换的资源池看起来比实际小一个数量级。
- **判据写在正则里**就必然误伤：`limit` 同时是「限流」和「额度上限」。要么收紧模式串，要么分级处理（临时 vs 永久）。
- 统计口径要能自证：`used = 0` 却标 `exhausted` 是"从未成功过就被判死"的铁证 —— 账本里留 `used` 字段的价值就在这里。
